# 拷问式需求澄清（Grilling）

目标：在动手前把设计树走完，**不留任何被默默假设的分支**。适用于 M/L 级变更的 RFC 前置，
也适用于任何"方案有好几条路"的时刻。

## 设计树与前线的定义

- **设计树**：每个决策会分出挂在它下面的子决策。根是"要做什么"，叶子是"具体怎么写"。
- **前线（frontier）**：所有**前置条件已经确定**的决策 —— 也就是说，现在就能问、不需要猜测未听到的答案的那些问题。

## 按轮次推进

一轮问**整条前线**，然后停下来等用户回答。绝不在同一轮里问一个依赖同轮另一问题的问题。

轮次格式：

```
❓ **Q1** - **<问题标题>**：<正文，可以多段，可以列选项>

➡️ <推荐答案>

---

❓ **Q2** - **<问题标题>**：<正文>

➡️ <推荐答案>
```

要求：

- **每个问题附上自己的推荐答案**，措辞要让用户回一句"yes"就等于采纳推荐。
- 用户答完一轮后，已定的决策把前线向外推，解锁原本被挡住的问题；**重算前线**再问下一轮。
- 结束条件：**前线为空** + 用户确认双方理解一致。此后才动 RFC 或代码。

## 事实归你，决策归用户

- 需要事实（上游 Kura 怎么做的、某个类有哪些字段、现有代码什么结构）→ **自己去查**
  （`grep` / `read` / 上游只读仓库），或派 subagent 查，**不要问用户他能让你查出来的东西**。
- 需要取舍（要不要引入抽象、快照要不要兼容旧版本、这个功能做多深）→ 交给用户，然后等。

查证类问题不要阻塞整轮：派出去之后，把不依赖该事实的问题先问掉。

## 用项目硬约束预剪枝（本项目的关键差异）

**提问前先读** `CLAUDE.md` 的「硬约束清单」与 `.claude/rules/08-additional-rules.md`，
把已被约束排除的选项**直接从设计树里剪掉**，不要作为备选问出来。例如：

- 不要问"要不要用 Lombok / MapStruct / Hutool 减少样板代码" —— 已禁止。
- 不要问"要不要引入 OSGi 那套服务跟踪" —— 已禁止。
- 不要问"快照 JSON 字段名能不能简化" —— 只可追加，不可改。
- 不要问"Controller 里直接调 Repository 行不行" —— 分层由 ArchUnit 强制。
- 不要问"要不要给 api 模块加 Spring 依赖" —— 只允许 JDK + Jackson 注解。

把这些当作**已定的前置事实**，只在它们导致真实取舍时才问（例如"上游快照里这个字段语义模糊，
我们追加一个 v2 键还是复用原有键"）。

## 产出

拷问结束，决策落到 `.claude/.change/rfc/NNN-<slug>.md`（RFC 里写清每个决策与理由，
"因为"是承重的）。若结论只是"这事不做"，也写进 RFC 或直接告知用户，别让它蒸发。

## 反模式

- **一次问 20 个问题**：会把依赖关系问错位。按轮次来。
- **没有推荐答案的提问**：把思考成本推回给用户，等于没干活。
- **问之前先动手**：理解了 70% 就开始写代码，剩下的 30% 会以返工的形式回来。
- **替用户拍板**：自己的推荐和用户的决定冲突时，按用户的。
